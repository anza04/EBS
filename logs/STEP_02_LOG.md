## 3. Implementation summary
- **Domain:** 17 entity types in feature folders (`Countries`, `Competitions`, `Seasons`, `Clubs`, `Players`, `Staff`, `Contracts`, `Matches`, `Standings`). All derive from `Entity<TId>`, take a strongly typed ID (`readonly record struct XxxId(Guid)` implementing `IEntityId<T>`) and validate every constructor argument, throwing `DomainValidationException` (a `DomainException`). Relationships are by ID only, with no navigation properties. `PlayerAttributes` (8 ratings, 1–100) and `BoxScore` are value objects owned by `Player` and `PlayerMatchStatistics`.
- **Added entity:** `CompetitionParticipant` (club × competition × season). It is not in the roadmap list, but a club needs it to take part in several competitions and to record its division each season.
- **Services:** ports `IRepository<TEntity, TId>` (`FindAsync`, `ListAsync(predicate)`, `Add`, `Remove`), `IUnitOfWork.SaveChangesAsync`, and `DataConstraintException`.
- **Persistence:** `EbmDbContext` with conventions: a generic `EntityIdConverter<T>` is registered for every ID type, keys are never generated by the database, and every foreign key is restrict-on-delete. Fluent mappings live in `Configurations/` and add unique indexes, a filtered unique index for the current club spell, and check constraints mirroring the domain rules. `EfRepository<,>` and `EfUnitOfWork` translate `DbUpdateException` into `DataConstraintException`. `DatabaseInitializer` (a hosted service) migrates the database at host start and logs the schema version. `DesignTimeDbContextFactory` is used by `dotnet ef`. Foreign keys are switched on in the connection string.
- **Migration:** `20261109114155_InitialSchema` creates 17 tables.
- **Hosting:** `AppPaths.DatabasesDirectory`/`DatabaseFile` (`<DataRoot>\databases\ebm.db`), passed to `AddPersistence(path)`.

## 5. Architecture and technical decisions
- **Strongly typed GUID IDs assigned by the application.** They are permanent and unique across databases, imports and save games, and mixing up IDs of different entities fails to compile. Version 7 GUIDs are time-ordered, so SQLite indexes stay compact. Imports (Step 03) can supply stable IDs from data files.
- **No navigation properties in the domain.** Entities refer to each other by ID. This keeps aggregates small, avoids accidental lazy graphs and keeps the domain free of EF concerns. Queries join explicitly through repositories.
- **Restrict-on-delete everywhere** enforces "historical data must be preserved" in the database itself. The only cascade is `PlayerAttributes` → `Players` (owned data).
- **Rules duplicated as check constraints.** The domain gives player-readable errors; the schema guarantees integrity against imports, editors or SQL that bypass the domain.
- **Competition rules as a JSON object column**, validated as an object by the domain and by `json_valid`/`json_type`. Its schema belongs to Step 04, so a typed model is not introduced yet.
- **Statistics record the club represented**, so player and club history are both correct after transfers.
- **Initialisation through a hosted service.** It runs on `host.StartAsync()`, which the desktop app and tests already call, so Desktop needs no reference to Persistence. A migration failure becomes a startup failure (exit code 2), which avoids running against an unknown schema.
- **Generic repository plus unit of work.** Specific query repositories are added when a use case needs them (no speculative APIs). `DataConstraintException` is deliberately not a `DomainException`: callers that can explain it (the Step 03 editor) catch it; anywhere else it is unexpected.
- **Money as whole euros (`long`).** SQLite has no decimal type, so integer amounts stay exact and sortable.
- **Enums stored as names** for readable, reorder-safe data.

## 8. Known limitations
- Player attributes are an initial set of 8 ratings (1–100). Step 05 defines the final catalogue; adding attributes needs a migration.
- Competition rules are any JSON object; Step 04 defines and validates the rule schema.
- Overlap between closed club spells and loans is not checked; only "one current spell per player" is enforced. Transfers (Step 08) add the rules.
- Entities expose only the mutators needed now (`Competition.UpdateRules`, `Club.ChangeHomeArena`, `Player.UpdateAttributes`, `PlayerClubHistoryEntry.Close`, `LeagueStanding.RecordResult`). The Step 03 editor adds the edit operations it needs.
- There is no save-game handling yet; there is one game database per data root.
- The shell window does not show database information; the schema version is in the log.
