## 3. Implementation summary
- **Club** (`Ebm.Domain.Clubs.Club`): `City` (optional, arena city as fallback), `Reputation`, `Balance`,
  `WageBudget`, `BoardExpectation` enum, set through `UpdateProfile`; constructor unchanged, documented defaults.
- **Roster domain** (`Ebm.Domain.Rosters`): `RosterRole` (Starter, Rotation, Bench, Inactive, Youth; first team and
  matchday helpers), `PlayerAvailability` from injury status, `RosterSpot` entity (lineup position only for starters,
  rotation order only for rotation; `MoveTo` for club changes), `SquadRules` (squad size, matchday size,
  recommended rotation, foreign/domestic limits, minimum age) and the pure `RosterValidator`
  (`Validate` / `ValidateRegistration` → `RosterValidation` of coded errors and warnings).
- **Competition registration**: `RegistrationRules.Squad` (`registration.squad` in the rules JSON, defaults =
  `SquadRules.Default`, validated with the rest of the rules).
- **Service** `IClubService` (`Ebm.Services.Clubs`): `GetProfileAsync` (country, city, arena, current season and
  competitions, wage bill, budget left, roster), `GetRosterAsync` (players with role, availability, foreign flag,
  contract flag, evaluation; club validation plus one registration check per current competition),
  `SaveRosterAsync` (all roles at once; rotation order = list order; stale spots moved/dropped), `AssignPlayerAsync`
  (closes the open spell, opens one at the new club, moves the spot). `ClubRoster.Check` and `RosterPlayer.ToMember`
  let the UI validate unsaved changes with exactly the service's rules.
- **Screens**: *Club profile* (details, finances, competitions, squad summary) and *Squad* (editable role,
  "Starts at" and rotation number per player, starting-five panel with effective ratings and familiarity, live issue
  list for the club and each competition, save/discard, add a player to the squad); *Clubs* editor gains the new
  fields (`ViewModels/Clubs/ClubViewModels.cs`, `Themes/Clubs.xaml`).
- **Import**: optional club columns `city`, `reputation`, `balance`, `wageBudget`, `boardExpectation`
  (`FieldReader.OptionalLong` / `OptionalEnum`).
- **Data**: sample dataset gets club profiles for all 14 clubs and 9 more Aurora Milano players (12-man squad,
  5 foreign, one 18-year-old prospect); templates show the new club columns. Generated by a deterministic script
  (not shipped).

## 5. Architecture and technical decisions
- **Membership is derived, roles are stored.** Who plays for a club comes from the existing club history and
  contracts (same rule as the player profile), so nothing is duplicated. Only the squad role is new state, one
  `RosterSpot` per player; a missing spot means "bench", so imports, editor moves and old databases need no roster
  data to work.
- **Roster spots are current state, not history**: they move with the player (`MoveTo`) and are dropped when he
  leaves; career history stays in `PlayerClubHistory` (decision 11 is unaffected).
- **Validate, don't block.** Only per-spot invariants (starter ↔ lineup position, rotation ↔ order) are domain
  rules; everything else is a coded issue from a pure validator, so a squad can be saved half-finished and the UI
  shows exactly what is wrong. Later steps decide what an invalid roster prevents (e.g. the match engine).
- **Data-driven registration.** Club defaults are a code record (`SquadRules.Default`, like `RatingModel`); each
  competition overrides them in its rules JSON, so league-specific limits (foreign players, squad size, minimum age)
  are data. Checked against the competitions of the current season (earliest season not yet ended).
- **Same rules in UI and service.** The squad screen re-validates unsaved edits through `ClubRoster.Check` and
  `RosterPlayer.ToMember`, the code the service uses, so the live result equals the saved one.
- **Rotation order from list order**: the service renumbers 1..n, so the order can never have gaps or duplicates.
- **EF default-value sentinel.** `HasDefaultValue(MidTable)` on an enum made EF skip `WinTitle` (CLR default 0)
  and store `MidTable`; found in the screenshot review, fixed with `HasSentinel((BoardExpectation)(-1))` and
  covered by a test (decision 26).
- Recorded as decisions 24–26 in `PROJECT_STATE.md`.

## 8. Known limitations
- Assigning a player to a club does not create, end or move contracts (Step 07); a moved player shows "no contract"
  at his new club and still counts towards the old club's wage bill until then.
- Availability uses the injury status only; fitness, suspensions and international duty come later (Steps 08, 22).
- Homegrown/locally trained rules, shirt numbers, registration deadlines and mid-season registration changes are not
  modelled. Squad roles cannot be imported.
- Board expectations, balance and wage budget are stored and shown but no game system uses them yet (Steps 12, 27);
  the wage bill counts player contracts only (staff from Step 27).
- The squad screen sets roles with drop-downs and rotation numbers; there is no drag-and-drop and no automatic
  lineup suggestion (AI squad selection is Step 13).
